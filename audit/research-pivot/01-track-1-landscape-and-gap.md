## 1. Scope

I mapped the literature around the repo's actual mechanism: *an LLM synthesizes a Python tool, generates its own pytest suite, "verifies" it, embeds it, stores it in a vector DB, and retrieves it semantically for later reuse.* That mechanism sits at the intersection of five literatures:

1. **Skill-library agents** (Voyager and descendants)
2. **LLM tool creation** (LATM, CREATOR, CRAFT, TroVE, ToolMaker, Live-SWE-agent)
3. **LLM test generation and the oracle problem** (test adequacy, mutation testing, metamorphic/property-based testing)
4. **Self-improving / self-modifying agents** (Reflexion, ADAS, Gödel Agent, Darwin Gödel Machine)
5. **Library learning / abstraction** (DreamCoder, LILO, Stitch)

Out of scope: RL-trained tool use, multimodal agents, security/sandbox escape research.

**What I was checking for:** whether any prior system *hardens the oracle that admits a tool into the library*, and whether anyone measures *how often a "verified" synthesized tool is actually wrong.*

**Grounding of the repo's own claims (verified in code, this session):**

| Claim | Reality | Evidence |
|---|---|---|
| "Test-Driven Development" | On test failure the engine **rewrites the failing tests** with regex, then retries; if still failing it registers the tool anyway as `experimental` | `src/synthesis_engine.py:148` (`_apply_aggressive_test_fixes`), `:212` (`re.sub(r'def test_[^:]*:\s*pass\s*\n', '', fixed_code)`), `:332`, `:343` ("FALLBACK: Register tool anyway as 'experimental'"), `:369` (`"tests_passed": False, "experimental": True`) |
| "Auto-tuning / Bayesian optimization" | `optimal = 0.45` is hardcoded; candidates are scored by distance to it. Reranking weights hardcoded to `[0.65, 0.25, 0.1]` | `src/auto_tuner.py:165`, `:348` |
| Working test suite | `pytest --collect-only` → **10 collection errors, 0 tests collected** | verified this session |
| Demo domain | e-commerce CSV profit margins — **no ground-truth oracle exists** | `tools/calculate_profit_margins.py` |

The repo's central pathology — *mutating the test until it agrees with the code* — is a literal, mechanized instance of the "circularity of error" that the testing literature warns about. That is not just an embarrassment; **it is the phenomenon the pivot should study.**

## 2. Grounding notes (sources actually fetched)

### Skill libraries / tool creation

✅ **Voyager: An Open-Ended Embodied Agent with Large Language Models** — Wang, Xie, Jiang, Mandlekar, Xiao, Zhu, Fan, Anandkumar (2023). https://arxiv.org/abs/2305.16291 (also fetched https://arxiv.org/html/2305.16291v2)
- Three components: automatic curriculum; ever-growing skill library of executable code; iterative prompting with environment feedback, execution errors, and **self-verification**.
- **Self-verification is a second GPT-4 agent acting as a critic**, not an environment oracle. Quoted: *"we instantiate another GPT-4 agent for self-verification. By providing Voyager's current state and the task to GPT-4, we ask it to act as a critic"*.
- **Skills are added to the library only after self-verification passes**: *"This iterative process repeats until self-verification validates the task's completion, at which point we add this new skill to the skill library."*
- Retrieval: embedding of the **program description** (generated by GPT-3.5); top-5 skills retrieved.
- **It reports no metric on skill reuse rate, library size vs. utility, or skill correctness.** Ablation shows removing the library causes a plateau; that is all.
- ⇒ **The repo is Voyager with pytest instead of Minecraft, and with a weaker critic.** This is the single most important fact in this document.

✅ **Large Language Models as Tool Makers (LATM)** — https://arxiv.org/abs/2305.17126, https://arxiv.org/html/2305.17126v2
- Tool maker (strong LLM) writes a Python utility; tool user (cheap LLM) applies it. Cost amortization is the pitch.
- **It does have a verification step:** *"the tool maker generates unit tests using validation samples and subsequently executes these tests on the proposed tool"* — and the assertion form is `assert ans == the provided answer`, i.e. **against ground-truth answers**.
- But: **3 validation samples**, **max 3 retries**.
- Notable: *"self-correction rarely occurs — only 2 out of 60 trials"* showed the tool maker successfully fixing itself from error messages.
- ⇒ LATM's oracle is **independent but instance-local (N=3)**. A tool can pass 3 GT instances and be wrong across the rest of its input domain. It is never verified at the level of its *contract*.

✅ **CRAFT: Customizing LLMs by Creating and Retrieving from Specialized Toolsets** — https://arxiv.org/html/2309.17428
- Pipeline: create → **validate** → deduplicate → retrieve.
- Validation: *"The validation step ensures the correctness of the created tools. This is achieved by examining whether the abstract tool functions can solve the original problems."* Tools that produce incorrect answers on the **original problem (with its ground-truth answer)** are discarded.
- Dedup: group by function name + arity; GPT-4 picks the most general.
- Retrieval: multi-view (problem text, function name, docstring), majority vote over 3 views.
- **Does not measure tool reuse rate.**
- ⇒ Again: **independent oracle, but instance-local (N=1 seed problem).**

✅ **TroVE: Inducing Verifiable and Efficient Toolboxes for Solving Programmatic Tasks** — Wang, Fried, Neubig, ICML 2024. https://arxiv.org/abs/2401.12869, https://arxiv.org/html/2401.12869v1
- **"Verifiable" means human-verifiable, not oracle-verified.** Tool admission is by **self-consistency / inter-execution agreement**: *"we select programs only by their inter-execution agreement"*; sample ~3K (function, solution) pairs, drop non-executing ones, pick the modal output.
- Human study: TroVE enables **31% faster human verification**.
- **Trimming:** remove functions used fewer than λ times, λ = C·log₁₀(n) with C = 0.5 → **74–90% smaller toolboxes**.
- ⇒ TroVE's admission oracle is **self-consistent (not independent)**. Its contribution to "library economics" is frequency-based trimming.

🔍 **CREATOR: Tool Creation for Disentangling Abstract and Concrete Reasoning of LLMs** — Qian, Han, Fung, Qin, Liu, Ji. Findings of EMNLP 2023. https://aclanthology.org/2023.findings-emnlp.462/ , https://arxiv.org/html/2305.14318v3
- Four stages: Creation, Decision, Execution, **Rectification** (rectify-on-error). Creates one tool per test case at inference time.
- ⇒ Admission signal is **execution success + LLM rectification** — self-consistent, no independent oracle. [Details from search snippet + abstract; I did not read the full method section.]

🔍 **ToolMaker / "LLM Agents Making Agent Tools"** — https://arxiv.org/pdf/2502.11705 (KatherLab, ACL 2025). Turns GitHub repos into LLM tools via **closed-loop self-correction**. ⇒ self-consistent admission.

✅ **Live-SWE-agent: Can Software Engineering Agents Self-Evolve on the Fly?** — https://arxiv.org/abs/2511.13646
- Starts with basic bash tools and **creates custom tools/scripts at runtime**. 77.4% on SWE-bench Verified; 45.8% on SWE-Bench Pro.
- **The abstract says nothing about verifying the tools it creates, and does not establish that tools persist across tasks.** Treat as ephemeral, unverified tool creation. [Persistence and verification: **UNVERIFIED** — not stated in the abstract I read.]

🔍 **Agent Workflow Memory (AWM)** — ICML 2025. https://icml.cc/virtual/2025/poster/45496 — induces reusable workflows; +24.6% / +51.1% relative success on Mind2Web / WebArena.
🔍 **SkillWeaver**, 🔍 **Agent Skill Induction (ASI)**, 🔍 **SkillFlow** (https://arxiv.org/pdf/2504.06188), 🔍 **Skill-Pro** (https://arxiv.org/pdf/2602.01869) — web-agent skill induction. Relevant because **SkillFlow reports a skill use rate of 68.8% against an oracle rate of 69.2%, and Skill-Pro reports reuse rate as a headline metric.** ⇒ **Reuse rate is already an established metric in this subfield.**

### The 2026 papers that circle this exact space (highest-priority threats)

✅ **EvolveTool-Bench: Evaluating the Quality of LLM-Generated Tool Libraries as Software Artifacts** — Kaliyev (UT Austin), Maryanskyy (Uber). arXiv:2604.00392v1, **1 April 2026**. https://arxiv.org/html/2604.00392v1 · code: https://github.com/abekek/evolvetool-bench
- Six **library-level** metrics: **code reuse rate, redundancy/duplication, composability, regression stability, dead code, quality gate.**
- Per-tool **Tool Quality Score (TQS)** = correctness (**hidden unit tests**) + robustness (adversarial inputs) + generality (held-out data) + code quality.
- **Finding 3: "Untested code is worse than no code."** One-shot generation (38.3% library health) *underperforms* the no-evolution baseline (41.4%).
- **Finding 5:** mean TQS is only **0.34–0.35**, with *"correctness weakest — hidden tests catch defects self-generated tests miss."*
- Headline: systems with near-identical task completion (63–68%) differ by up to **18% in library health**; ARISE has the *lowest* task completion but the *highest* EvolveTool Score.
- Stated limitations: **two models, one provider; automated checks only; no statistical significance testing.**
- ⇒ **THIS IS THE #1 NOVELTY THREAT.** It has already published the *observation* that self-generated tests over-certify, and it has already occupied *library economics* (reuse rate, dead code, redundancy, rot). **It is, however, a diagnostic benchmark — it does not propose or evaluate an intervention, it never isolates the conditional probability P(tool wrong | tool admitted), and it does not test whether hardening the admission oracle changes downstream outcomes.**

✅ **Tool-Genesis: A Task-Driven Tool Creation Benchmark for Self-Evolving Language Agent** — Xia, Hu, Wang, Jin, Jiao, Lu, Li, Luo. arXiv:2603.05578, **5 March 2026**. https://arxiv.org/abs/2603.05578 · https://tool-genesis.github.io
- Four levels: surface compliance → semantic interface fidelity (Schema-F1) → functional correctness (**9,441 held-out unit tests**, boundary/negative cases) → downstream utility (oracle-normalized success with a fixed agent).
- Verification is **execution-grounded against ground-truth reference tools**, not LLM-generated tests.
- Key finding: SOTA models struggle in one-shot; *"minor initial flaws are amplified through the pipeline, leading to a precipitous drop in downstream metrics."* GPT-5.1: 33% downstream success direct-prompting → 60.4% with code-agent repair loops.
- Their **"Signal–Validation Alignment"** analysis shows interface-level metrics are **weak proxies for downstream utility** — models can pass intermediate checks and still ship non-functional tools.
- ⇒ **Threat #2.** Also a diagnostic benchmark. It establishes that *intermediate verification signals mislead*, which is adjacent to my thesis, but it studies **interface/schema signals**, not the **self-generated-test signal**, and it proposes no oracle-hardening gate.

### Test oracles, adequacy, and correlated failure (the mechanism)

✅ **Do LLMs generate test oracles that capture the actual or the expected program behaviour?** — Konstantinou, Degiovanni, Papadakis (2024). https://arxiv.org/abs/2410.21136
- 24 open-source Java repos; developer-written and auto-generated tests; compared to EvoSuite.
- Headline: *"LLM-based test generation approaches are also prone [to] generating oracles that capture the **actual** program behaviour rather than the **expected** one."*
- Also: LLMs are better at *generating* oracles than at *judging* externally generated ones; LLM oracles had higher fault-detection potential than EvoSuite's.
- ⇒ **This is the canonical statement of the mechanism.** A test written in the presence of code encodes what the code *does*, not what it *should* do.

✅ **Measuring the Influence of Incorrect Code on Test Generation** — Huang, Zhang, Harman, Du, Cui (2024). https://arxiv.org/abs/2409.09464
- 11 LLMs, 3 benchmarks + 41 real-world examples.
- When shown **incorrect** code instead of correct code, generated tests degrade sharply: **−57% test accuracy, −12% coverage, −24% bug detection**; on real-world code, **47% worse bug-detection rate**.
- ⇒ **The oracle is worst precisely when it is needed most.** In a synthesis loop the LLM tests *its own* code, so whenever the code is wrong the test suite is systematically degraded. This is the causal core of the gap.
- Note: it does **not** report how often a generated test *asserts the buggy behaviour* — that specific quantity is [UNVERIFIED / not measured in the abstract I read].

✅ **Estimating Correctness Without Oracles in LLM-Based Code Generation** — Valentin, Madadi, Sapia, Böhme. arXiv:2507.00057. https://arxiv.org/html/2507.00057v1
- Proposes **incoherence**: sample multiple independent programs; if two disagree on an input, at least one is wrong.
- Detects **~66–69% of incorrect programs with no false positives**; Spearman 0.92–0.94 vs oracle-based ranking. When incoherence = 0, error rate still **19% on MBPP**.
- ⇒ Important calibration: **even the best oracle-free method leaves ~1/3 of errors undetected, and a "clean" signal still corresponds to a 19% error rate.** Oracle-free verification does **not** close the problem. Good news for the thesis; also a baseline I must beat/compare against.

✅ **Consistency Meets Verification (ConVerTest)** — Taherkhani et al. arXiv:2602.10522. https://arxiv.org/html/2602.10522
- Self-consistency + chain-of-verification + dual execution agreement, **without ground-truth solutions**. Test validity +39%, coverage +28%, mutation score +18%.
- **But**: it treats LLM-refined code as a *proxy* for ground truth — an explicitly circular dependency — and it operates on **isolated unit-test generation, not a skill-library loop.**
- ⇒ Not a killer. It is a strong *baseline arm* for the intervention experiment.

✅ **Scoring Verifiers: Evaluating Synthetic Verification for Code and Reasoning** — arXiv:2502.13820. https://arxiv.org/abs/2502.13820
- Converts benchmarks into scoring/ranking datasets (HE-R, HE-R+, MBPP-R, MBPP-R+) to evaluate synthetic verifiers. Reasoning improves test generation; scaling test count improves verification accuracy.
- Whether it reports a **false-positive rate** for synthetic verification is **[UNVERIFIED]** — not stated in the abstract I read. Its framing is RL-reward / ranking, not library admission.

🔍 **EvalPlus / "Is Your Code Generated by ChatGPT Really Correct?"** — Liu, Xia, Wang, Zhang. NeurIPS 2023. https://arxiv.org/abs/2305.01210 · https://github.com/evalplus/evalplus
- **HumanEval → HumanEval+ (80× more tests, 164 → 13k+); MBPP → MBPP+ (35×).** Test inputs from LLM + mutation-based synthesis; the **oracle is the human-written canonical solution**.
- **Top models' pass@k drops 19–29% under the stronger suite.** Test insufficiency causes mis-ranking.
- ⇒ **This is both my strongest prior and my primary evaluation instrument.** It proves that a *human-written* test suite already over-certifies by 19–29 points. A suite written by the same model that wrote the code should be *strictly worse*. That gives me a quantitative floor for the headline prediction.

🔍 **MuTAP** — "Effective test generation using pre-trained LLMs and mutation testing." https://arxiv.org/pdf/2308.16557 (+ ScienceDirect / https://github.com/ExpertiseModel/MuTAP). Re-prompts the LLM with **surviving mutants** until they are killed; reaches **mutation score 93.57%**, detects up to **28% more faulty human-written snippets**.
🔍 **Mutation-Guided Unit Test Generation with a LLM** (https://arxiv.org/pdf/2506.02954) and **Mutation-Guided LLM-based Test Generation at Meta** — same family, deployed at scale.
🔍 **Test vs Mutant: Adversarial LLM Agents for Robust Unit Test Generation** — https://arxiv.org/pdf/2602.08146 (2026).
- ⇒ **The oracle-hardening intervention EXISTS — but only in the software-testing literature, applied to standalone unit-test generation. It has never been placed at the admission gate of a tool-synthesis skill library, and its effect on library-level outcomes has never been measured.**

🔍 **Validating LLM-Generated Programs with Metamorphic Prompt Testing** — https://arxiv.org/abs/2406.06864. Detects **75% of erroneous GPT-4 programs at 8.6% FPR** by checking semantic consistency across paraphrased prompts.
🔍 **Use Property-Based Testing to Bridge LLM Code Generation and Validation** — https://arxiv.org/html/2506.18315v1. "Property-Generated Solver": validate invariants rather than exhaustive I/O oracles.
🔍 **Correlated Errors in Large Language Models** — https://arxiv.org/pdf/2506.07962. LLM errors are correlated, and **correlation is higher for models from the same developer / same base architecture**; as models improve they *converge* in the errors they make.
- ⇒ This is the theoretical justification for the "independent adversarial test author" arm, and it predicts that **decorrelation should scale with model-family distance.**

## 4. Gap statement

Every tool-synthesis and skill-library system admits a synthesized tool into its permanent library on the strength of an oracle that is either **(a) self-consistent** — the same model (or model family) that wrote the code also writes or adjudicates the check: Voyager's GPT-4 critic, TroVE's inter-execution agreement, CREATOR's rectify-on-error, ToolMaker's self-correction, and this repo's self-written pytest — or **(b) independent but instance-local**: LATM validates against 3 ground-truth samples, CRAFT against the single seed problem it was born from. Case (a) is provably compromised, because tests written in the presence of code encode what the code *does* rather than what it *should* do (Konstantinou et al., arXiv:2410.21136), and test quality collapses precisely when the code is wrong (−57% test accuracy, −24% bug detection; Huang et al., arXiv:2409.09464). Case (b) certifies a tool on the instances it was derived from and then lets a semantic retriever reuse it across a distribution it was never verified on. The consequence is a quantity **nobody has ever reported: the False Admission Rate, FAR = P(tool violates its contract | tool passed verification and entered the library).** EvolveTool-Bench (arXiv:2604.00392, Apr 2026) comes closest — it notes that "hidden tests catch defects self-generated tests miss" and that mean tool quality is only 0.34 — but it is a *diagnostic benchmark*: it never isolates FAR as a conditional, never tests an intervention, and reports no significance. **My claim: FAR is large (I predict ≥ 20%, floored by EvalPlus's finding that even *human-written* HumanEval tests over-certify by 19–29 points); FAR is predicted by the *adequacy* of the admission suite (its mutation score), not by its size or pass rate; and a cheap, LLM-independent hardening gate at admission reduces FAR by ≥ 50% relative at < 3× synthesis cost — buying more downstream task success per dollar than spending the same budget synthesizing more tools.** This is falsifiable in every clause, and it is the *only* claim in this repo's vicinity that is not already taken.

### Pressure-testing the two candidates the parent proposed

**Candidate A — Verification integrity. VERDICT: SURVIVES, but must be repositioned.**
- ✅ Nobody reports FAR as a conditional probability. Nobody hardens the *admission* oracle. Nobody measures the library-level consequence of a falsely-admitted tool.
- ⚠️ **The *observation* is partially scooped.** EvolveTool-Bench (Apr 2026) already published "self-generated tests miss defects hidden tests catch." Tool-Genesis (Mar 2026) already published "intermediate verification signals are weak proxies for downstream utility." **If the thesis is "we show self-generated tests over-certify," it is 3 months late and dead.**
- ✅ **The repositioning that saves it:** the contribution is **(i) the conditional/causal quantity (FAR and its dependence on suite adequacy), (ii) the intervention (an oracle-hardening admission gate), and (iii) the library-amplification consequence (a falsely-admitted tool is retrieved and reused, so verification debt compounds with reuse count).** None of that is published.

**Candidate B — Library economics. VERDICT: KILL AS A STANDALONE THESIS.**
- ❌ **Reuse rate is measured**: EvolveTool-Bench (code reuse rate, dead code, redundancy, regression stability, composability); SkillFlow (68.8% use rate vs 69.2% oracle); Skill-Pro (reuse rate as headline).
- ❌ **Library rot / trimming is solved**: TroVE removes functions used < λ = 0.5·log₁₀(n) times, shrinking toolboxes 74–90% with *higher* accuracy.
- ❌ **Abstraction quality is a mature field**: DreamCoder / LILO / Stitch optimize a principled compression objective; "when does an abstraction pay for itself" is literally the MDL objective they minimize.
- ✅ **What survives:** the *interaction* — break-even reuse count as a function of FAR. That is not a paper on its own; it is **an analysis section inside Thesis 1**, and I fold it there.

### 🥇 T1 — **The Self-Consistent Oracle Problem: false admission in LLM tool synthesis, and what it costs to fix**

**Precise claim.**
When an LLM synthesizes a tool and verifies it with a test suite that the same model authored, the pass/fail signal is a *systematically biased* certificate. Define **FAR = P(tool violates its contract | tool passed its self-generated suite and was admitted)**. FAR is large; it is governed by the **adequacy** of the admission suite (measured by mutation score), not by its size, coverage, or pass rate; and it can be substantially reduced by an **admission gate** that hardens or decorrelates the oracle — at a cost that is *lower per unit of downstream success* than spending the same budget synthesizing more tools.

**Falsifiable predictions (each kills the thesis if it fails).**

| ID | Prediction | Kill condition |
|---|---|---|
| **P1** | FAR ≥ 20% for self-generated suites, measured against EvalPlus's independent oracle. *Floor justified: EvalPlus shows even human-written HumanEval tests over-certify by 19–29 points; a same-model suite should be strictly worse.* | **FAR < 5% ⇒ thesis dead.** The self-consistent oracle is good enough and hardening buys nothing. |
| **P2** | The **mutation score** of the self-generated suite (against the tool's own code) predicts FAR; test *count* and *coverage* do not. | If mutation score is uncorrelated with FAR, the "adequacy" mechanism is wrong and the gate design is unmotivated. |
| **P3** | An admission gate (mutation-kill requirement + metamorphic/property-based relations) cuts FAR by **≥ 50% relative at < 3× synthesis cost**. | < 10% relative reduction ⇒ hardening is not the answer. |
| **P4** (library) | A library with a FAR-gated admission policy beats an ungated library on downstream task success, **and the gap widens with reuse count** (verification debt compounds). | If the gap is flat in reuse count, the "amplification" claim — the thing that makes this a *library* problem and not a *codegen* problem — dies. |
| **P5** (mechanism) | An independent adversarial test author reduces FAR, and the reduction **scales with model-family distance** between coder and tester (cross-family > same-family > self). *Motivated by "Correlated Errors in LLMs" (2506.07962).* | If same-family ≈ cross-family, correlated error is not the mechanism. |

**How I'd measure it.**
- **Ground-truth oracle:** EvalPlus (`pip install evalplus`) — HumanEval+ / MBPP+ hidden tests + human-written canonical solutions. **Completely independent of the synthesizing LLM.**
- **FAR:** synthesize tool + self-generated pytest suite → admit iff suite passes → evaluate admitted tools against EvalPlus. FAR = (admitted ∧ fails EvalPlus) / (admitted).
- **Adequacy:** AST-level mutation operators (comparison flips, off-by-one, boundary swaps, condition negation, arithmetic op swaps) → mutation score of the self-generated suite. CPU-only, no `mutmut` dependency needed.
- **Gate arms:** (0) self-generated suite [status quo], (1) + mutation-kill requirement (MuTAP-style, re-prompt on surviving mutants), (2) + property-based relations via `hypothesis`, (3) + independent adversarial test author who never sees the implementation, (4) ConVerTest-style consistency baseline (2602.10522), (5) incoherence baseline (2507.00057).
- **Cost normalization:** LLM calls and wall-clock per admitted-and-correct tool. **This is the number that makes it a research result and not a demo.**
- **Model ladder:** run across 3 capability tiers so FAR-vs-capability is a *curve*, not a point (this also de-risks the "frontier model has no headroom" problem — see Residual Risk R2).

**Scores.**
- **Novelty 4/5.** The *observation* is partially scooped by EvolveTool-Bench (Apr 2026) and Tool-Genesis (Mar 2026) — I must cite both and position against them explicitly. The *conditional quantity*, the *intervention at the admission gate*, the *adequacy-predicts-FAR* mechanism, and the *reuse-amplification* result are all unpublished. Docking a point for the scoop risk, honestly.
- **Feasibility 5/5.** EvalPlus is pip-installable. Mutation operators are ~150 lines of `ast`. `hypothesis` is pip-installable. Zero GPU, zero network beyond LLM API, deterministic, fast. **This is genuinely an overnight core.**
- **Evaluability 5/5.** The oracle is external, exact, and standard. Every prediction has a number and a kill condition.
- **Total: 14/15. RANK 1.**

**Why it's the right thesis:** it converts the repo's *worst bug* (`_apply_aggressive_test_fixes` mutating tests until they agree with the code) into the *object of study*. The system already contains a perfect negative control.

### 🥈 T2 — **Verification-aware retrieval: adequacy as a first-class ranking signal**

**Precise claim.**
Skill libraries retrieve on semantic similarity alone (Voyager: embedding of the program description; CRAFT: multi-view name/docstring/problem similarity). But a tool's *verification strength* is orthogonal to its *semantic fit*, and a well-matched but weakly-verified tool is worse than a slightly-worse-matched but strongly-verified one. **Claim: a retriever that ranks on `similarity × verification-adequacy` beats a similarity-only retriever at equal library size — and the effect is larger the higher the library's FAR.**

**Falsifiable prediction.**
Adding a per-tool verification-confidence term (mutation score of the tool's admission suite, plus a contract-coverage term) to the reranker improves downstream task success at matched library size and matched retrieval budget. **Kill condition:** no improvement, or improvement not modulated by FAR ⇒ verification strength carries no retrieval-relevant information and the idea is dead.

**How I'd measure it.** Requires T1's machinery (every tool carries a mutation score). Library setting with a reuse signal; ablate reranker: similarity-only vs similarity × adequacy vs adequacy-only. Report downstream success and *silent corruption rate* (fraction of task failures attributable to retrieving a falsely-admitted tool).

**Scores.**
- **Novelty 5/5.** I found **no** prior work that puts verification strength into a skill-retrieval ranking. Voyager and CRAFT rank on similarity; EvolveTool-Bench measures library health but does not feed it back into retrieval.
- **Feasibility 4/5.** It is a reranker — cheap — but it *depends on T1* and needs a domain with a real reuse signal, which MBPP+ does not provide. More moving parts.
- **Evaluability 3/5.** Needs a constructed compositional suite (see §6, Domain 2); more room for reviewer suspicion of a hand-tuned benchmark.
- **Total: 12/15. RANK 2.**

**Relationship to T1: T2 is the natural second contribution of the *same* system.** T1 produces a mutation score per tool as a by-product; T2 spends it. Build T1; if there is time, T2 is nearly free. Do not scope T2 as an independent project.

---

### 🥉 T3 — **Library economics: break-even reuse under verification uncertainty**

**Precise claim.** A synthesized-tool library pays for itself only above a break-even reuse count R\* that grows with FAR: a falsely-admitted tool has *negative* expected value that scales with how often it is retrieved, so R\*(FAR) determines whether "synthesize once, reuse forever" beats "re-synthesize each time."

**Scores.**
- **Novelty 2/5.** **Largely occupied.** EvolveTool-Bench measures reuse rate, dead code, redundancy, regression stability. TroVE already trims by usage frequency (74–90% reduction). DreamCoder/LILO/Stitch already optimize a principled "does this abstraction pay for itself" objective (compression / MDL). The *only* fresh element is conditioning on FAR — which is T1's variable.
- **Feasibility 4/5.** Evaluability 3/5.
- **Total: 9/15. RANK 3 — DO NOT PURSUE STANDALONE. Fold the FAR-conditioned break-even analysis into T1 as one figure.**

---

**Recommendation: lock T1. Carry T2 as a stretch contribution. Fold T3 into T1 as an analysis.**

## 6. Ranked domains, with criteria stated first

### Criteria (stated before scoring, in priority order)

| ID | Criterion | Why it matters |
|---|---|---|
| **C1** | **Ground-truth oracle that is INDEPENDENT of the LLM writing the code, and CONTRACT-LEVEL (not instance-level)** | **HARD REQUIREMENT.** Without it, FAR is unmeasurable and the thesis is untestable. *Contract-level* matters because LATM (3 GT samples) and CRAFT (1 seed problem) already have instance-level oracles — reusing that design would replicate the exact flaw I am criticizing. |
| **C2** | Real reuse signal: tasks share sub-capabilities so a library can actually compound | Required for P4 (amplification) and for T2. |
| **C3** | Edge-case density: the domain must contain traps where the model's *code* misconception and its *test* misconception plausibly coincide | If not, FAR ≈ 0 by construction and the experiment is uninformative regardless of the truth. |
| **C4** | No GPU, no network, no external API, deterministic, fast | Overnight feasibility. |
| **C5** | Tunable difficulty | Lets me draw a FAR-vs-difficulty curve rather than report a point. |
| **C6** | Public benchmark / reviewer-recognized | Credibility with an Anthropic/OpenAI reader. |

### Scoring

### Which candidates fail the independent-oracle test (C1)

**Hard failures:** the **current e-commerce CSV demo** (no oracle exists — the system is unfalsifiable by construction) and any **LLM-as-judge** setup. **Soft failure:** **GSM8K/math** — it has ground truth, but only at the *instance* level, which is the same under-certification I am attacking; adopting it would be self-defeating.

### Recommendation

**Primary: MBPP+ (EvalPlus).** It buys the headline number (FAR) on a public, standard, reviewer-trusted oracle, with prior work (19–29 pt over-certification by *human* tests) giving me a principled floor for the prediction.
**Secondary: a constructed reference-library differential-testing suite.** It buys the contract-level oracle and the reuse signal MBPP+ lacks, which are required for P4 and T2. **Freeze the task list before running anything** (see R4).

Using both is not hedging — it is necessary: **MBPP+ has the credible oracle but no reuse; the reference-library suite has the reuse but no public standing.** Neither alone supports the full thesis.

## 7. What we will NOT claim

1. **We do not claim general self-improvement.** The system does not modify its own architecture, prompts, or policy. ADAS, Gödel Agent, and the Darwin Gödel Machine do that; we do not, and we will not imply it.
2. **We do not claim the auto-tuner learns anything.** It is being deleted, not defended. No "policy optimization," no "Bayesian search," no "learned thresholds."
3. **We do not claim TDD.** The current pipeline rewrites failing tests. Any surviving claim will be stated as *"LLM-generated test suites used as an admission oracle,"* never as *"test-driven development."*
4. **We do not claim SOTA on any benchmark.** We are measuring a property of a verification procedure, not competing on pass@k. We will not put a leaderboard number in an abstract.
5. **We do not claim novelty in tool synthesis, skill libraries, semantic retrieval, or composite/abstraction promotion.** All are prior art (§3). Our contribution is confined to the *admission oracle* and its downstream consequences.
6. **We do not claim we were first to notice that self-generated tests are weak.** EvolveTool-Bench (Apr 2026) and Tool-Genesis (Mar 2026) got there first, and we will cite them prominently. We claim the *conditional quantification*, the *intervention*, and the *library-level amplification*.
7. **We do not claim security or sandbox-escape guarantees.** Docker execution is an engineering convenience, not a safety result.
8. **We do not claim our FAR estimate generalizes across model families, languages, or domains.** We will report it as a curve over a small model ladder on Python, and say so.
9. **Our N is small.** We will report bootstrap CIs and effect sizes, we will pre-commit to the analysis, and we will not report a p-value we did not plan for.
10. **We do not claim the hardened gate is optimal or cheapest.** We claim it is *better than the status quo at a stated cost multiple*. Someone will find a cheaper gate; that is fine.
11. **We do not claim contamination-freedom.** MBPP/HumanEval are heavily contaminated. We will state this and argue why it *sharpens* the result (see R5) rather than pretending it away.

## 8. Residual risk

| ID | Risk | Severity | Mitigation |
|---|---|---|---|
| **R1** | **EvolveTool-Bench (arXiv:2604.00392, Apr 2026) scooped the observation.** It already reports that self-generated tests miss defects hidden tests catch, and already measures reuse rate / dead code / redundancy. It is 3 months old. | **HIGH — the single biggest threat.** | Novelty must live in the **intervention** and the **conditional/causal framing**, not the observation. Cite it in the first paragraph, state exactly what it did, and state exactly what it did not do (no conditional FAR, no intervention, no significance testing, 2 models / 1 provider). **If we do not cite it, a reviewer finds it and the work is dead.** |
| **R2** | **No headroom.** If the synthesizing model is frontier-class, its base error rate on MBPP+ is low, so FAR has little room to be large — and P1 (FAR ≥ 20%) could fail for an uninteresting reason. | **HIGH** | Report FAR across a **model ladder** (3 capability tiers). The scientifically invariant quantity is the **over-certification factor** — how much the self-generated suite overstates correctness relative to the independent oracle — not the raw FAR. A FAR-vs-capability *curve* is a stronger result than a point estimate, and it is robust to this failure. **Decide the ladder before running.** |
| **R3** | **Mutation saturation.** MBPP+ functions are small; a rich operator set may still generate too few mutants for mutation score to be a discriminative signal (P2). | MEDIUM | Report mutants-generated-per-tool. If saturated, fall back to *property-violation count* under `hypothesis` as the adequacy proxy. Pre-specify this fallback. |
| **R4** | **Constructed-benchmark suspicion.** The reference-library suite is authored by us → reviewer assumes cherry-picking toward tasks the model fails. | MEDIUM–HIGH | **Freeze the task list before any model is run**, and derive tasks from the reference library's *public API surface / documentation*, never from observed model failures. Publish the frozen list with the result. |
| **R5** | **Contamination.** MBPP/HumanEval are in every training set. | MEDIUM | State it. Then note it *strengthens* the finding: if the model has effectively memorized the solution and its self-written suite *still* over-certifies, the oracle problem is worse than a clean benchmark would show. Optionally add a small LiveCodeBench-recent slice (arXiv:2403.07974) as a contamination check. |
| **R6** | **Statistical power.** Small N; multiple arms; easy to overclaim. | MEDIUM | Pre-register predictions P1–P5 with kill conditions (already written above). Bootstrap CIs. Report effect sizes. No unplanned p-values. |
| **R7** | **Tool-Genesis (arXiv:2603.05578) overlaps on "intermediate signals mislead."** | MEDIUM | It studies *interface/schema* signals, not the *self-generated-test* signal, and proposes no gate. Distinguish explicitly in related work. |
| **R8** | **The intervention is "just" MuTAP applied in a new place.** A reviewer may call it an engineering transfer. | MEDIUM | This is why **P4 (reuse amplification) and T2 (adequacy-as-retrieval-signal) matter** — they are the parts that are *specific to libraries* and cannot be reduced to "run MuTAP." If P4 fails, the work degrades to a solid empirical note, not a contribution. Be honest about that in advance. |
| **R9** | Live-SWE-agent's tool persistence/verification is **[UNVERIFIED]** — I read only the abstract. | LOW | Read the full paper before writing related work. If it *does* persist and verify tools, it becomes a closer ancestor than currently assessed. |
